# Модуль 2 · Grounding, інструменти (Tools) та корпоративний LLM Gateway

У цьому модулі мультиагентна система Loan Copilot переходить від абстрактного планування діалогу (Webinar 1) до взаємодії з реальною інформаційною екосистемою банку. Агент отримує дві фундаментальні спроможності:
1. **Очі (Grounding / Заземлення):** методи безпечного та достовірного вилучення знань із внутрішніх банківських джерел без галюцинацій та без виходу за межі дозволеного контексту.
2. **Руки (Tools / Інструменти):** детерміноване виконання дій у зовнішніх реєстрах, базах даних та core banking із гарантіями цілісності, аудиту та безпеки запису.

## 1. Меню заземлення: 6 архітектурних патернів (Grounding ≠ RAG)

Одна з найпоширеніших помилок архітекторів-початківців — намагання застосувати векторний RAG до всіх типів даних без розбору. У банківському середовищі вибір методу заземлення визначається трьома вимірами: **структурою даних**, **вимогами до свіжості** та **критичністю детермінованості**.

```
                           ЯКИЙ ТИП ДАНИХ?
        ┌───────────────────────┼───────────────────────┐
   Текстові регламенти      Таблиці / Цифри         Зв'язки / Entities
        │                       │                       │
   Чи вміщується весь      Semantic Layer /        GraphRAG
   корпус у контекст        Text-to-SQL
   (< ~100–150 стор.)
   та чи він стабільний?
   ┌────┴────┐
  ТАК       НІ (великий масив або часті оновлення)
   │            │
Long Context    Яка структура документу?
+ Cache         ┌───────┴───────┐
            Ієрархічний     Невпорядкований
            (НБУ / закони)   (FAQ / Wiki)
                │               │
            PageIndex       Hybrid RAG
            (ToC tree)      (BM25 + Dense + Rerank)
                                │
                    Яка критичність точності?
                    ┌───────────┴───────────┐
                Звичайна                Банківський аудит
                    │                       │
                Naive RAG           Contextual Retrieval
                                    + Self-RAG / CRAG loop
```

### 1. Vector / Hybrid RAG (Векторний та гібридний пошук)
* **Форма даних:** Великі масиви неструктурованого або слабкоструктурованого тексту.
* **Застосування у банку:** Корпус внутрішніх кредитних політик (`POL-LOAN-*`), операційні процедури (`SOP-CREDIT-*`), публічні довідники продуктів, FAQ.
* **Обмеження:** Не підходить для точних числових обчислень, балансів та агрегатів.

### 2. Semantic Layer / Text-to-SQL (Семантичний шар над реляційними даними)
* **Форма даних:** Реляційні бази даних, сховища DWH (ClickHouse, Snowflake, PostgreSQL), транзакційні таблиці.
* **Чому векторний RAG тут небезпечний:** Якщо запитати у векторної бази *«Який середній щомісячний обіг позичальника за останні 6 місяців?»*, ретрівер витягне кілька випадкових рядків транзакцій, а LLM галюцинує суму. Векторні моделі не вміють робити SQL-агрегації `SUM`, `AVG`, `GROUP BY`.
* **Архітектурне рішення:** Семантичний шар (Cube.dev, dbt Semantic Layer, Vanna.ai). Він описує типізовані бізнес-метрики та зв'язки таблиць. Модель генерує валідований SQL-запит, який повертає детерміноване число.

### 3. Hierarchical / PageIndex (Ієрархічний пошук по дереву змісту)
* **Форма даних:** Багаторівневі регуляторні акти (Постанови Правління НБУ, закони України, типові генеральні договори).
* **Проблема плаского чанкінгу:** Постанова НБУ № 351 складається з розділів, статей та підпунктів. Якщо розділити її на чанки по 500 токенів, підпункт *«в) коефіцієнт приймається рівним 0.8»* втрачає зв'язок зі статтею і стає беззмістовним сміттям.
* **Архітектурне рішення:** PageIndex зберігає деревоподібну структуру документа (Table of Contents). Модель спочатку знаходить релевантний розділ, потім спускається до статті, зберігаючи батьківський контекст.

### 4. Long-Context + Prompt Caching (Пряме завантаження корпусу з кешуванням)
* **Форма даних:** Текстовий корпус (document corpus), який повністю вміщується в контекстне вікно моделі (< ~100–150 сторінок) і рідко оновлюється (раз на місяць чи квартал).
* **Суть методу:** Якщо всі правила споживчого кредитування банку займають до 150 сторінок, їх можна взагалі не ділити на чанки та не створювати векторну базу. Документ поміщається безпосередньо у системний промпт моделі з довгим контекстом. Сучасні хмарні платформи підтримують кешування промптів (Prompt Caching), надаючи знижку 80–90% на повторні звернення.
* **Перевага:** 100% усунення проблеми «ретрівер не знайшов потрібний чанк».

### 5. Direct Tools & Code Sandbox (Прямі виклики API та виконання коду)
* **Форма даних:** Актуальні залишки на рахунках, курси валют, статус паспорта у держреєстрах, складні математичні формули.
* **Принцип:** Мовні моделі погано рахують ануїтетні графіки платежів та формули навантаження на дохід (PTI/DTI). Усі розрахунки обов'язково виносяться у детерміновані Python-функції або in-process SQL (DuckDB). Агенту повертається точний математичний результат.

### 6. GraphRAG (Графи знань та зв'язків сутностей)
* **Форма даних:** Мережі пов'язаних юридичних та фізичних осіб, корпоративні групи, ланцюжки власності.
* **Застосування у банку:** Перевірка кінцевих бенефіціарних власників (UBO), виявлення шахрайських груп (fraud rings), перевірка пов'язаності з публічними діячами (PEP). Звичайний текстовий пошук не здатен пройти ланцюжок із 3 компаній та 2 номінальних директорів.

## 2. Контрольні цикли RAG: Naive, Self-RAG та Agentic RAG (Control Loops)

Архітектурний вибір між лінійним конвеєром та автономним плануванням:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. NAIVE RAG (1-Shot):                                                 │
│    Query ───► Search (top-K) ───► Prompt ───► Generate                 │
│    Характеристика: Швидко (300ms), дешево, але сліпа генерація.       │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────┐
│ 2. SELF-RAG & CRAG (Self-Reflection):                                  │
│    Query ───► Search ───► [Grade Docs] ───► Generate ───► [Verify] ↺   │
│                              │                         │               │
│                              ▼                         ▼               │
│                        Rewrite / Fallback          Refusal Gate        │
│    Характеристика: Самооцінка релевантності та фактчекінг.             │
│    Обов'язковий стандарт для кредитного регламенту.                    │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────┐
│ 3. AGENTIC RAG (Autonomous Multi-Source):                              │
│    Query ───► Intent ───► Plan ───► Route to [Vector / SQL / API] ↺    │
│    Характеристика: Агент сам обирає джерела та ітеративно шукає дані.   │
│    Застосовується для повного розгляду заявки позичальника.            │
└────────────────────────────────────────────────────────────────────────┘
```

## 3. Інженерний RAG: 6 сходинок індексації та пошуку (Retrieval & Indexing Pipeline)

Перехід від наївного хакатонного RAG до промислового рішення охоплює як етап підготовки бази (**Indexing Time**), так і етап виконання запиту (**Retrieval Time**):

| Етап життєвого циклу | # | Техніка | Що робить | Коли застосовувати | Приріст якості |
|---|---|---|---|---|---|
| **Retrieval Time** | **1** | **Hybrid Search (BM25 + Dense)** | Паралельний пошук: BM25 шукає точні слова та номери, Dense — семантичний зміст. Результати зливаються через Reciprocal Rank Fusion (RRF). | Обов'язково для банківських текстів, де є точні номери статей (Постанова № 351), ІПН та розмовні синоніми. | +20–30% до Recall |
| **Indexing Time** | **2** | **Contextual Retrieval (Anthropic)** | До кожного чанка перед ембедінгом додається 1–2 речення контексту всього документа (назва регламенту, розділ, сфера). | Усуває проблему «сліпих чанків», коли відірваний абзац не містить назви продукту. | Знижує помилки ретрівера на ~40% |
| **Indexing + Retrieval** | **3** | **ColBERT / Late Interaction** | Токен-рівневі ембедінги та матричне порівняння (MaxSim) без стиснення всього тексту в один вектор. | Юридичні договори, де кожен номер та юридичне застереження мають значення. | Максимальна точність на специфічних термінах |
| **Post-Retrieval** | **4** | **Cross-Encoder Reranking** | Двоетапний пошук: швидкий бі-енкодер знаходить 20–30 кандидатів, а важка модель переранжування зіставляє їх із запитом. | Піднімає найбільш релевантний пункт правила з нижніх позицій (#7–10) на Top-1. | +15–25% до точності Top-1 |
| **Indexing Time** | **5** | **RAPTOR Summary Trees** | Рекурсивна кластеризація та багаторівнева сумаризація чанків у дерево ще під час індексації. | Концептуальні запити високого рівня (наприклад, *«Яка загальна філософія банку щодо кредитного ризику під час воєнного стану?»*). | Покриває наскрізні теми |
| **Pre-Retrieval** | **6** | **Query Rewrite / HyDE** | Генерація гіпотетичної відповіді банківською мовою або розбиття запиту на підзапити ДО звернення до бази. | Долає лексичний розрив між просторіччям клієнта та канцелярською мовою регламенту. | Піднімає Recall на неоднозначних запитах |

### Детальний розбір 6 технік із банківськими прикладами та схемами

#### 3.1. Hybrid Retrieval: чому вектори сліпнуть на номерах законів

```
                   Запит: «Постанова № 351 критерії дефолту»
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                               ▼
     Dense Vector Search (Семантика)      BM25 Lexical Search (Точні слова)
     Знаходить: подібний текст            Знаходить: точний збіг токена "351"
     (Плутає Постанову 351 і 352!)        (Але сліпий до синонімів)
                  │                               │
                  └───────────────┬───────────────┘
                                  ▼
                   Reciprocal Rank Fusion (RRF)
            RRF_score(d) = Σ [ 1 / (60 + rank_i(d)) ]
                                  │
                                  ▼
                    Ідеальний Top-1: REG-NBU-351
```

* **Реальний кейс у банку:**
  * У нормативній базі є **Постанова Правління НБУ № 351** (оцінка кредитного ризику за кредитами) та **Постанова НБУ № 352** (бухгалтерський облік активів).
  * Для векторної моделі (Dense) ці два документи мають семантичну схожість **97%** — вектори не розуміють різниці між однією цифрою «1» та «2» у номері нормативу! Векторний ретрівер із ймовірністю 50% притягне не ту постанову.
  * **BM25** шукає точний строковий токен `"351"` та `"дефолт"`. Він безпомилково відсікає постанову 352.
  * Натомість, коли позичальник запитує розмовною мовою: *«як регулятор визначає неплатоспроможність позичальника?»*, у BM25 немає слів «Постанова 351», і він не знаходить нічого.
  * **Рішення:** Гібридний пошук паралельно запускає обидва рушії та зливає їх через формулу **RRF (Reciprocal Rank Fusion)**, забезпечуючи ідеальне попадання в обох сценаріях.

#### 3.2. Contextual Retrieval (Anthropic): як усунути «сліпі чанки»

Коли великий регламент автоматично нарізається на фрагменти по 400 токенів, більшість абзаців у середині тексту втрачають суб'єкт та контекст:

```
┌────────────────────────────────────────────────────────────────────────┐
│ СЛІПИЙ ЧАНК (Звичайний RAG):                                           │
│ «У випадках, передбачених цим пунктом, ставка збільшується на 2.5%    │
│ річних, а максимальний термін кредитування скорочується до 12 місяців.»│
│                                                                        │
│ ❌ Проблема: Про яку ставку йдеться? Для фізосіб чи ФОП? За іпотекою  │
│ чи автокредитом? Який це банк? Векторний пошук тут безсилий.           │
└────────────────────────────────────────────────────────────────────────┘
                                    │
                  Додаємо Contextual Retrieval (Haiku / 4o-mini)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ ЗБАГАЧЕНИЙ ЧАНК (Contextual Chunking):                                │
│ [Контекст: Регламент POL-LOAN-01 ПриватБанку. Розділ 4: Спеціальні     │
│ умови кредитування ФОП 3-ї групи без забезпечення застави]             │
│ «У випадках, передбачених цим пунктом, ставка збільшується на 2.5%    │
│ річних, а максимальний термін кредитування скорочується до 12 місяців.»│
│                                                                        │
│ ✔ Результат: Чанк знайдеться за будь-яким запитом про штрафи для ФОП!  │
└────────────────────────────────────────────────────────────────────────┘
```

* **Інженерний ефект:** Зменшує пропуски потрібних фрагментів на **35–45%** ціною копійчаного одноразового запуску дешевої моделі на етапі створення індексу.

#### 3.3. ColBERT / Late Interaction: збереження точних токенів

На відміну від класичних бі-енкодерів, які стискають весь текст у 1536 чисел, ColBERT зберігає **окремий вектор для кожного токена**:

```
Звичайний Bi-Encoder (Dense):
Текст чанка (300 слів) ───► Стиснення в 1 вектор [0.12, -0.45, ...] ──► Втрата дрібних деталей

ColBERT (Late Interaction):
Запит:    [Постанова]  [№]  [351]  [дефолт]
             │          │     │        │
             ▼          ▼     ▼        ▼        (Токен-до-токена матриця схожості MaxSim)
Документ: [Постанова]  [№]  [351]  [розділ] [IV] [кредитний] [ризик] [дефолт]
```

* **Чому це важливо для банківських юристів:**
  Якщо в договорі написано *«Комісія 0.5% сплачується позичальником, крім випадків наявності зарплатної картки»*, одне маленьке слово *«крім»* кардинально змінює юридичний зміст. У звичайному усередненому векторі слово «крім» розчиняється серед 300 інших слів. ColBERT гарантує збереження точного збігу таких критичних часток і цифр.

#### 3.4. Cross-Encoder Reranking: двоетапний пошук (Two-Stage Retrieval)

Чому ми не шукаємо важкою моделлю відразу по всій базі? Тому що вона повільна. Тому архітектура будується у два етапи:

```
Етап 1: Ретрівер (Recall)              Етап 2: Cross-Encoder (Precision)
Швидкий відбір 10 кандидатів           Глибока оцінка пари (Запит, Чанк)
Час: ~25–35 мс                         Час: ~80–110 мс

[База знань банку]                      [10 відібраних кандидатів]
       │                                         │
       ▼                                         ▼
10 кандидатів (швидкий бі-енкодер)      Cross-Encoder пропускає через шари
· #1 POL-LOAN-01 §3 (Загальні ліміти)   уваги запит і документ РАЗОМ:
· #2 POL-LOAN-01 §1 (Сфера)             · Чанк #1 (загальні ліміти) ──► Скор: 0.18
...                                     ...
· #7 SOP-CREDIT-02 §3 (Матриця 4-Tier)  · Чанк #7 (точна матриця)  ──► Скор: 0.94 🚀
                                                 │
                                                 ▼
                                        Top-1: SOP-CREDIT-02 §3 (Матриця ставок)!
```

* **Реальний кейс у нашому стенді:**
  Запит: *«Які процентні ставки кредитування та матриця рішень діють за рейтингом позичальника?»*.
  Первинний гібридний пошук витягнув 10 чанків, але через спільні загальні слова точна таблиця з матрицею 4-Tier опинилася аж на **#7 позиції** (поза типовим лімітом Top-3 для системного промпту!).
  Cross-Encoder глибоко зіставив зміст правила із запитом позичальника і перемістив матрицю рішень на **перше місце в промпті**, усунувши ризик галюцинації ставки.

#### 3.5. RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval): піраміда узагальнень для макро-запитів

**Розшифровка абревіатури (дослідження Stanford University, ICLR 2024):**
* **R — Recursive** (Рекурсивний): кластеризація та узагальнення повторюються шар за шаром, поки не буде побудовано все дерево.
* **A — Abstractive** (Абстрактивний): мовна модель створює якісне синтезоване резюме своїми словами, а не просто висмикує уривки речень.
* **P — Processing** (Обробка тексту).
* **T — Tree-Organized** (Організоване у дерево): листя дерева — це первинні сирі чанки, а гілки та корінь — узагальнені макро-концепції.
* **R — Retrieval** (Пошук): ретрівер одночасно шукає як серед детальних фактів (листя), так і серед високорівневих резюме (гілки).

Звичайний RAG ефективний для **точкових запитань**, але безсилий для **концептуальних тем**:

```
           [Рівень 2: Загальна кредитна стратегія банку]
                                  ▲
                  ┌───────────────┴───────────────┐
       [Резюме: Оцінка платоспроможності]  [Резюме: Робота з дефолтами]  (Рівень 1)
                  ▲                               ▲
        ┌─────────┴─────────┐           ┌─────────┴─────────┐
    [Чанк 1] [Чанк 2] [Чанк 3]      [Чанк 4] [Чанк 5] [Чанк 6]   (Рівень 0 - сирий текст)
```

* **Порівняння двох типів запитань:**
  * **Точкове запитання (Point Query):** *«Який штраф за прострочення понад 30 днів?»*
    → Пошук іде на **Рівень 0** і витягує конкретний абзац із пункту 5.2.
  * **Концептуальне запитання (Macro Query):** *«Яка загальна філософія банку щодо кредитування малого бізнесу під час воєнного стану?»*
    → У регламенті немає жодного окремого абзацу з такою відповіддю, це тема всього 50-сторінкового документа!
    → Пошук знаходить узагальнення на **Рівні 1 або 2** піраміди RAPTOR. Модель отримує макро-структуру та дає всебічну, структуровану відповідь топ-менеджеру.

#### 3.6. Query Rewrite та HyDE: міст між сленгом клієнта та мовою банку

Клієнт у мобільному застосунку та банківський юрист говорять різними мовами:

```
КРОК 1 · Запит клієнта у Privat24:
«Хочу перекредитуватися, бо старий відсоток сильно кусається, можна платити менше?»
       │
       ▼
КРОК 2 · Швидка LLM генерує гіпотетичну відповідь банківською мовою (HyDE):
«Процедура рефінансування діючої кредитної заборгованості за програмою зі зниженням
процентної ставки та оптимізацією щомісячного графіка погашення ануїтету...»
       │
       ▼
КРОК 3 · Векторизується ГІПОТЕЗА, а не кострубатий запит клієнта!
       │
       ▼
КРОК 4 · Збіг 96% із офіційним документом:
Знайдено: SOP-CREDIT-02 §5 «Порядок рефінансування та дисконтування ставок»!
```

* **А що таке Query Rewrite у багатокроковому діалозі?**
  Якщо клієнт у четвертому повідомленні чату пише: *«А якщо я ФОП?»* — для бази знань ця фраза з 4 слів марна.
  **Query Rewrite** дивиться на історію контексту і перетворює її на повноцінний запит:
  > *«Вимоги, ліміти та винятки щодо беззаставного кредитування на суму 150 000 грн для позичальників у статусі ФОП»*.
  Тепер ретрівер відбирає саме пункт 4.2.1 регламенту банку.

## 4. Корпоративна топологія векторних сховищ (Vector Storage Topology)

Перше запитання, яке Solution Architect чує від служби інформаційної безпеки (InfoSec) та команди експлуатації (Operations): **«Куди саме ми кладемо вектори, хто це адмініструватиме о 3-й ночі, і чи потрібен нам новий окремий софт у Kubernetes?»**.

У банківській екосистемі існує три головні архітектурні варіанти:

```
                            ДЕ ЗБЕРІГАТИ ВЕКТОРИ У БАНКУ?
        ┌───────────────────────────────────┼───────────────────────────────────┐
   pgvector (PostgreSQL)           Dedicated (Qdrant / Milvus)          OpenSearch / Elastic
        │                                   │                                   │
   ✅ Дефолт №1 для 80% систем         ✅ Екстремальний скейл               ✅ Якщо Elastic вже є
   · Вже погоджений InfoSec           · 50M+ векторів (транзакції)         · BM25 + Lucene k-NN разом
   · ACID разом із реляційними даними · QPS > 500–1000                     · Єдина пошукова шина банку
   · Обсяг до 2–5 млн векторів        · ⚠️ Окремий кластер у K8s           · ⚠️ Потребує багато RAM
```

### Порівняльна матриця для Solution Architect:

| Критерій | `pgvector` (PostgreSQL) | Dedicated (Qdrant / Milvus) | OpenSearch / Elasticsearch |
|---|---|---|---|
| **Погодження InfoSec** | **Найпростіше.** PostgreSQL вже є в контурі, сертифікований, має узгоджені мережеві доступи. | **Складне.** Потребує аудиту безпеки нового бінарного ПЗ, сканування образів K8s. | **Просте**, якщо кластер Elastic вже розгорнутий у банку для логів чи каталогу. |
| **ACID-транзакційність** | **Повна.** Вектори зберігаються в одній транзакції з клієнтськими даними та метаданими. | **Eventual Consistency.** Немає транзакційного зв'язку з реляційною базою банку. | **Near Real-Time.** Затримка індексації ~1 секунда (refresh interval). |
| **Експлуатація (Ops/DBA)** | **0 нових інструментів.** Працюють стандартні `pg_dump`, WAL-реплікація, моніторинг pg_stat. | **Окремий кластер.** Потрібні нові навички бекапу, моніторингу та шардингу вектора. | **Середні.** Вимагає досвідченої команди для тюнінгу heap memory та garbage collection. |
| **Підтримуваний обсяг** | Ідеально до **2–5 млн векторів** (індекси HNSW та IVFFlat). | **50+ млн векторів** без просідання latency. | До **20–30 млн векторів**. |
| **Гібридний пошук** | SQL запит об'єднує `tsvector` (повнотекст) + `pgvector` через `ORDER BY`. | Вбудований dense + sparse (BM25) з коробки. | Найкраща у світі реалізація повнотекстового BM25 + векторний k-NN плагін. |

> **Золоте правило для банку:** Якщо корпус регламентів банку разом із виписками займає до 2–5 млн фрагментів — **починайте з `pgvector`**. Це заощадить 2–3 місяці погоджень з InfoSec і використовує вже наявну інфраструктуру. Окрему базу (Qdrant) підключайте лише тоді, коли ви векторизуєте весь масив транзакцій Privat24 (десятки мільйонів рядків) з навантаженням сотні запитів на секунду.

## 5. Безпека документів (Document-Level Security): Пастка Post-filtering

У фінансовій установі база знань **ніколи не є публічною для всіх співробітників**:
* Публічні тарифи та загальні правила доступні всім (клієнтам, операторам чату).
* Внутрішні методики оцінки ризику та ліміти доступні лише кредитним андеррайтерам.
* Антифрод-правила та моніторинг підозрілих операцій доступні виключно службі комплаєнсу та безпеки.

### Чому Post-filtering — це критична архітектурна пастка:

```
❌ НАЇВНИЙ POST-FILTERING (Аварійний підхід):
1. Користувач (Оператор відділення) надсилає запит: «Які максимальні суми кредитування?»
2. Ретрівер робить векторний пошук по ВСІЙ базі ──► відбирає Top-10 векторів.
3. Усі перші 10 місць зайняли закриті інструкції Департаменту ризиків (гриф «Для службового користування»).
4. Бекенд перевіряє роль користувача і відкидає ці 10 чанків через відсутність прав!
5. РЕЗУЛЬТАТ: Оператор отримує 0 РЕЗУЛЬТАТІВ («Інформацію не знайдено»), хоча в базі є відкритий регламент!

─────────────────────────────────────────────────────────────────────────────

✔ IN-INDEX PRE-FILTERING (Банківський стандарт):
1. Роль та права користувача передаються БЕЗПОСЕРЕДНЬО у пошуковий запит.
2. Векторний індекс шукає найближчі вектори ВИКЛЮЧНО серед дозволених документів:
   WHERE allowed_roles && :user_roles AND effective_date <= CURRENT_DATE
3. РЕЗУЛЬТАТ: Top-5 релевантних документів, до яких користувач має фізичне право доступу!
```

* **Приклад SQL-запиту в `pgvector` з підтримкою DLS та контролю чинності:**
  ```sql
  SELECT 
      chunk_id,
      chunk_text,
      doc_code,
      1 - (embedding <=> :query_embedding) AS similarity_score
  FROM policy_chunks
  WHERE 
      -- 1. Document-Level Security (перетин масиву ролей документа з ролями користувача)
      allowed_roles && ARRAY['operator', 'public']::varchar[]
      -- 2. Контроль чинності норми (виключаємо майбутні та скасовані редакції)
      AND effective_date <= CURRENT_DATE
      AND (expiry_date IS NULL OR expiry_date > CURRENT_DATE)
  ORDER BY embedding <=> :query_embedding
  LIMIT 5;
  ```

## 6. Тріаж та діагностика збоїв RAG (RAG Failure Triage)

Коли система у продакшні видає некоректну відповідь, додавання інструкцій у системний промпт є неефективним. Архітектор використовує методологію локалізації відмов (на базі метрик RAGAS):

| Режим відмови | Симптом у банку | Першопричина | Архітектурний важіль усунення |
|---|---|---|---|
| **1. Hallucination (Низька Faithfulness)** | Модель вигадала неіснуючу ставку або пообіцяла списання 50% боргу. | Параметрична пам'ять пересилила наданий контекст. | **Citation Gate:** вимога цитувати конкретний `[§ SOP]`; примусовий **Refusal** за відсутності факту; `temperature=0`. |
| **2. Retrieval Miss (Низький Context Recall)** | Відповідь правильна в цілому, але пропущено важливий виняток для ФОП або норматив НБУ. | Поганий чанкінг розірвав текст; семантична невідповідність слів. | **Contextual Retrieval** (префікси до чанків); **Hybrid BM25**; збільшення пулу кандидатів (top-K=25) + Reranker. |
| **3. Factual / Math Error (Низька Correctness)** | Ретрівер підтягнув ліміт PTI (45%), але модель порахувала 48% як 42% і схвалила кредит. | Спроба виконувати арифметику мовною моделлю у промпті. | **«RAG для правил, Tools для математики»**. Винесення обчислень у Python/DuckDB tools із гарантією точності. |
| **4. Intent Drift (Низька Relevancy)** | Клієнт питав про реструктуризацію автокредиту, а бот відповів про тарифи на картку. | Запит неоднозначний; пошук спрацював за випадковими збігами слів. | **Intent Router** перед пошуком; уточнюючий діалог (Disambiguation turn); фільтрація за метаданими продукту. |

## 7. Контрактна модель інструментів (Tool Contracts & Write-Safety)

Кожен інструмент у банківському контурі повинен мати 4 обов'язкові гарантії:
1. **Pydantic Schema:** строга типізація та валідація параметрів на вході й виході.
2. **In-Code RBAC:** перевірка прав доступу виконується безпосередньо у коді Python/бекенду, а не в системному промпті (захист від Prompt Injection).
3. **Audit Trail:** незмінний запис у лог кожного виклику: мітка часу, ідентифікатор сесії, викликана функція, параметри, результат та вартість.
4. **Declared Side-Effect:** класифікація інструменту за типом впливу:
   - `none`: безпечні чисті обчислення (ануїтет, формули).
   - `read`: читання внутрішніх не-PII даних.
   - `external-read (PII)`: звернення до зовнішніх реєстрів з персональними даними (`credit_history.pull`). Вимагає обов'язкової фіксації **`consent_id`** (згода клієнта). Без згоди виклик блокується на рівні коду.
   - `write`: мутація стану рахунків чи створення заявки. Обов'язково вимагає **Idempotency Key** для запобігання дублюванню транзакцій під час повторних спроб (retries).

## 8. Корпоративний LLM Gateway (LiteLLM / DIAL)

Пряме підключення SDK мовних моделей у сервіси заборонено. Усі виклики проходять через централізований шлюз:
- **Безпека та приватність:** розгортання у приватному контурі (VPC / On-Prem), модулі DLP для автоматичного маскування номерів платіжних карток (PAN) та паспортів, угода про нульове збереження даних (Zero Data Retention).
- **Дворівнева маршрутизація (Tiered Routing):**
  - *Tier 1 (Fast / Small LLM):* дешеві та швидкі моделі для 80% рутини (інтент, вилучення сутності, грейдинг чанків).
  - *Tier 2 (Frontier / Reasoning LLM):* флагманські моделі лише для ухвалення остаточного рішення андеррайтингу.
  - *Ефект:* зниження вартості інференсу на одну заявку на 70–85%.
- **Кешування промптів (Prompt Caching):** кешування статичних кредитних політик зі знижкою до 90% вартості та скороченням часу до першого токена (TTFT).
- **Бюджетні ліміти та автоматичний Fallback:** встановлення лімітів витрат на заявку/користувача (захист від нескінченних агентних циклів) та автоматичне перемикання на резервний регіон у разі збоїв.
