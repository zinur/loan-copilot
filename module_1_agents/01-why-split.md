# 01 · Чому не монолітний prompt

## Learning objective

Зрозуміти, чому один «універсальний» prompt з усіма інструкціями —
анти-паттерн у production. Побачити конкретні провали на прикладі.

## Prerequisites

Нема. Це перший step.

## Narrative

Перший інстинкт, коли починаєш будувати AI copilot, — написати один
великий system prompt:

```
Ти loan assistant. Збери заявку, перевір KYC, викликай bureau,
прийми рішення, згенеруй контракт. Якщо є питання — спитай клієнта.
Ніколи не галюцинуй ставки. Будь ввічливий.
```

Воно працюватиме на демо. У production — провалиться. Чому?

**По-перше, context window.** Коли ви додасте SOP (Standard Operating Procedure — внутрішній регламент банку) на 50 сторінок,
regulatory text, 15 tools, історію клієнта — у вас не вистачить
tokens навіть для `gpt-4o`. А ціна за token × довжину prompt'а × кожен
turn ÷ 1000 клієнтів на день = ваш CFO плаче.

**По-друге, instruction interference.** Коли LLM бачить «збери заявку»
і «прийми рішення» в одному prompt'і, він намагається робити обидва
одночасно. На третьому turn він питає клієнта «а скільки у вас
кредитів» (bureau role), хоча ще не завершив KYC. Якість падає
експоненціально від кількості ролей в одному prompt'і.

**По-третє, тестування.** Як ви тестуєте моноліт? Потрібно побудувати
end-to-end сценарії, бо немає ізольованих боксів. Якщо `bureau` промт
регресує — ви побачите це лише у фіналі flow. У multi-agent системі ви
просто перезапустите eval'и на `BureauAgent`.

**По-четверте, зміни.** Compliance каже «з завтра KYC має запитувати
джерело коштів». У моноліті — редагуєте 2000 рядків prompt'а, ризикуєте
зламати іншу роль. У multi-agent — редагуєте один `KYCAgent`, тести на
інші 6 agent'ів все одно проходять.

**Pattern.** Один agent = одна відповідальність = один тестований контракт.

## Code

Протистояння стилей — без коду, у коментарях:

```python
# ❌ Anti-pattern: монолітний prompt
MONOLITH = """
Ти Loan Copilot. Твої обов'язки:
1. Зібрати full_name, tax_id, income, loan amount, term, purpose.
2. Перевірити KYC через call_kyc(tax_id).
3. Викликати bureau через call_bureau(tax_id).
4. Якщо score < 600, відмовити. Якщо > 700, схвалити. Інакше manual review.
5. Згенерувати контракт за template.
6. Запросити e-sign.
Ніколи не галюцинуй ставки. Завжди посилайся на SOP-2024-01.
"""

# ✓ Pattern: роль + контракт
INTAKE_SYSTEM = """
Ти Intake Agent для Loan Copilot. Твоя єдина задача — зібрати заявку.
Поля: full_name, tax_id, phone, email, monthly_income, amount, term, purpose.
Якщо чогось не вистачає — спитай клієнта. Якщо все є — поверни JSON за
схемою Application.
Не відповідай на питання про ставки, рішення, продукти — для цього є
інші agent'и.
"""
```

Різниця — у останньому рядку. **Intake agent відмовляється робити чужу
роботу.** Це запобігає прошкуванню.

## Try it

Відкрийте будь-який чат з LLM. Задайте йому `MONOLITH` як system prompt.
Напишіть: «Привіт, яка у вас ставка на 100 000 грн?».

Побачите: модель почне відповідати ставками, хоча ще не має даних
клієнта. Це називається **premature disclosure** — агент повідомляє
інформацію до того, як пройшов необхідні перевірки. У кредитуванні це
регуляторний ризик (Ст. 10 ЗУ «Про споживчий кредит»).

Тепер задайте `INTAKE_SYSTEM`. Запитайте те саме. Модель має відповісти:
«Я збираю заявку. Для відповіді про ставки потрібно спочатку завершити
intake + bureau check».
