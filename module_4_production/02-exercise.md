## Learning objective

На практиці підготувати кредитний копілот до промислової експлуатації та аудиту:
1. Оцінити три відповіді на QA-004 проти реально знайденого контексту; Golden Set (**20 еталонних кейсів**) вивчаємо як набір даних.
2. Розрахувати математичні метрики **RAGAS (Faithfulness, Answer Relevance, Context Recall)** — це підмножина для RAG-шару; повний набір — 7 родин метрик.
3. Перевірити суворий **Quality Gate**: runner повертає PASS або BLOCKED за порогами (код виходу 1 при провалі) у разі регресії якості чи витоку банківської таємниці. Інтеграція в CI/CD-пайплайн — поза скоупом воркшопу.
4. Зберегти персистентний артефакт рану для аудиту та налаштувати трейсинг у **Langfuse**.

---

## Що покажемо

Два сценарії, які відтворюються в коді:
1. **Регресія якості блокується:** галюцинована ставка або відсутня цитата роблять Faithfulness нижчою за поріг, і Quality Gate повертає BLOCKED (на кшталт випадку Air Canada).
2. **Банківська таємниця не виходить у логи:** номер картки (PAN) і незамаскований ІПН виявляються та маскуються детермінованим фільтром (Luhn).

### 1. Дослідіть Golden Set (`data/golden_qa.jsonl`)

Відкрийте файл `module_4_production/data/golden_qa.jsonl`:
* Перевірте структуру 20 еталонних кейсів:

  * 3 кейси KYC (санкції РНБО, статус PEP, прострочені документи).
  * 2 провокативні кейси Adversarial (спроби непрямої ін'єкції та випитування ваг скорингу).

### 2. Запустіть раннер оцінювання `src/run_eval.py`

Раннер бере питання QA-004 (ФОП, 4 місяці, 150 000 грн), **реально шукає контекст** у політиках (BM25 + Dense з модуля W2) і оцінює три **явно позначені фікстури-відповіді**: A точна з цитатою, B «красива вода», C галюцинація. Метрики й рішення гейту рахує код (відповіді — фікстури, а не вивід живої моделі).

```bash
python -m module_4_production.src.run_eval
```
* **Що перевірити у консолі:**
  1. Знайдений контекст (Top-4) містить POL-LOAN-01 §4.
  2. Таблиця трьох відповідей: A має Faithfulness 1.00, цитату й `PASS`; B і C мають `BLOCKED` (B без цитати, C з галюцинованою ставкою; їхня Faithfulness значно нижча).

  4. Створено артефакт рану `module_4_production/data/eval_runs/run_*.jsonl` (1 summary + 3 трейси).
  5. Код виходу `1`, бо gate для набору BLOCKED (дві з трьох відповідей навмисно погані).
* **Спробуйте самі:** додайте четверту відповідь у `QA004_CANDIDATES` (наприклад, коротку відмову без цитати) і подивіться, що вирішує gate.

### 3. Перевірте роботу фільтра банківської таємниці (Luhn Algorithm)

Відкрийте `module_4_production/src/eval_metrics.py`:
* Перевірте функцію `detect_pii_pan_leak(text)`:

### 3b. (Режим 2) Golden set через реальний CodeMie workflow

Той самий раннер може прогнати всі 20 кейсів `golden_qa.jsonl` через ваш workflow (`POST /v1/workflows/{id}/executions`, потім опитування статусу та читання output останнього вузла). Порівняння детерміноване: вердикт vs `expected_verdict`, цитата, PII, ін'єкція. Gate: decision accuracy ≥ 92% і жодного PII/ін'єкції.

```bash
export CODEMIE_API_URL=https://<host>/code-assistant-api
export CODEMIE_WORKFLOW_ID=<id>
export CODEMIE_COOKIE='_oauth2_proxy=...'   # значення Cookie із DevTools (короткоживуче, лише демо)
# або export CODEMIE_TOKEN=<bearer>; або CODEMIE_AUTH_URL + CODEMIE_CLIENT_ID + CODEMIE_CLIENT_SECRET
python -m module_4_production.src.run_eval --mode workflow --limit 3   # спершу 3 кейси
```

Workflow має повертати у фінальному вузлі JSON на кшталт `{"decision": "approve|reject|hitl_escalate|refuse_injection", "answer": "... POL-LOAN-01 §3.1"}`. Без поля `decision` вердикт вгадується за ключовими словами — це ненадійно. Форма відповіді запуску й ендпоінти взято з офіційного `codemie-sdk`; на вашому стенді перевірте один кейс вручну перед повним прогоном.

## Якщо застрягли

**Як RAGAS рахує Faithfulness?**
Faithfulness вимірює, чи кожне числове чи нормативне твердження відповіді підтверджене знайденим документом:
$$\text{Faithfulness} = \frac{|\text{Підтверджені твердження}|}{|\text{Усі твердження відповіді}|}$$
Якщо модель стверджує, що «максимальна сума 500 000 грн», а в наданій політиці написано «300 000 грн» — це твердження не проходить верифікацію і знижує бал.

**Чому не можна пушити сирі промпти в APM?**
Згідно зі Статтею 60 Закону України «Про банки і банківську діяльність», відомості про банківські рахунки та фінансовий стан клієнтів є банківською таємницею. Відправка незамаскованих даних у сторонні SaaS-платформи моніторингу створює ризик розголошення банківської таємниці та юридичної відповідальності. Саме тому деідентифікація (PII scrubbing) виконується до виходу з периметра банку — на рівні поду в Kubernetes або в OTel Collector — перед відправкою OpenTelemetry-спану.
